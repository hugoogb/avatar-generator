`@avatar-generator/web-component` ships a standards-based custom element, so you
can drop an avatar into any HTML page with no framework. It works equally well
inside React, Vue, Svelte, Solid, or anything else that can set a DOM property.

## From a CDN, with no build

One `<script>` tag gives you both elements and all fifteen styles, about 32 KB
gzipped. Choose a style with the `avatar-style` attribute:

```html
<script src="https://cdn.jsdelivr.net/npm/@avatar-generator/web-component@3"></script>

<avatar-generator avatar-style="faces" seed="ana" size="48" alt="Ana"></avatar-generator>
<avatar-generator-group avatar-style="faces" items='["ana","ben","chi"]' options='{"size":40}'></avatar-generator-group>
```

`https://unpkg.com/@avatar-generator/web-component@3` serves the same file,
`dist/avatar-generator.global.js`. The script also exposes everything in
`@avatar-generator/core`, plus `styles`, as `window.AvatarGenerator`:

```html
<script>
    const avatar = AvatarGenerator.createAvatar(AvatarGenerator.styles.pixels, { seed: "ana" });
</script>
```

<Aside title="Pin a version in production">
    `@3` follows the newest 3.x release, and a minor release can redraw a style. Pin an exact version, such as `@3.2.0`,
    if your avatars must not change. The browser bundle exists from 3.2.0.
</Aside>

## Installation

```bash
pnpm add @avatar-generator/core @avatar-generator/web-component @avatar-generator/style-initials
```

## Basic usage

Importing the package auto-registers `<avatar-generator>`. Set the JavaScript
properties `styleImpl` and `options` on the element:

```ts
import "@avatar-generator/web-component";
import { initials } from "@avatar-generator/style-initials";

const el = document.createElement("avatar-generator");
el.styleImpl = initials;
el.options = { seed: "Hugo GB", size: 64 };
el.setAttribute("alt", "Hugo GB");
document.body.append(el);
```

<Aside title="Why `styleImpl` and not `style`">
    Every `HTMLElement` already has a `style` property for inline CSS. Overriding it would break the platform, so the
    avatar style goes on `styleImpl`.
</Aside>

Setting `styleImpl` or `options` triggers an immediate re-render. Nothing
renders until both are set.

## Attributes, with a bundler

The attributes the CDN bundle uses work from npm too. Register the styles you
want to name with `registerStyle`, which uses the style's own name unless you
give another:

```ts
import { registerStyle } from "@avatar-generator/web-component";
import { faces } from "@avatar-generator/style-faces";

registerStyle(faces); // or registerStyle(faces, "team")
```

```html
<avatar-generator avatar-style="faces" seed="ana" size="48"></avatar-generator>
```

Elements already on the page render as soon as their style is registered. An
`avatar-style` naming a style nobody registered renders nothing.

When a property and an attribute set the same thing, the property wins:
`styleImpl` over `avatar-style`, and each key of `options` over the `seed`,
`size` and `options` attributes.

## Custom tag name

If `<avatar-generator>` collides with something in your app, register the
element under another name:

```ts
import { register } from "@avatar-generator/web-component";
import { initials } from "@avatar-generator/style-initials";

register("my-avatar");

const el = document.createElement("my-avatar");
el.styleImpl = initials;
el.options = { seed: "Hugo GB" };
document.body.append(el);
```

The extra name is registered alongside `<avatar-generator>`, not instead of it,
and `register` is safe to call more than once — a name that already exists is
ignored.

<Aside type="tip" title="Fixed in v3">
    `register(tagName)` could never succeed before v3. Importing the package
    binds `AvatarElement` to `<avatar-generator>`, and the registry allows one
    tag name per constructor, so any custom name threw `NotSupportedError`.
    Additional names now get their own subclass.
</Aside>

## Properties and attributes

| Name           | Kind      | Default    | Description                                                          |
| -------------- | --------- | ---------- | -------------------------------------------------------------------- |
| `styleImpl`    | property  |            | The avatar `Style` object                                            |
| `options`      | property  |            | Avatar options for that style                                        |
| `avatar-style` | attribute |            | Name of a style added with `registerStyle` (the CDN bundle adds all) |
| `seed`         | attribute |            | The seed                                                             |
| `size`         | attribute | `64`       | Size in pixels                                                       |
| `options`      | attribute |            | Any other options, as JSON: `options='{"square":true}'`              |
| `alt`          | attribute | `"Avatar"` | Alt text for the internal `<img>`                                    |

An avatar renders once it has a style (`styleImpl` or `avatar-style`) and a
seed (from `options` or `seed`).

`<avatar-generator-group>` takes `styleImpl`, `items` and `options` as
properties, or `avatar-style`, `items` (a JSON array) and `options` (JSON) as
attributes, plus `alt`.

## Styling

The element renders its `<img>` inside an open shadow root, so page CSS does not
reach inside it. Size and position the host element itself:

```css
avatar-generator {
    display: inline-block;
    border-radius: 50%;
    overflow: hidden;
}
```

The shadow root is open, so `el.shadowRoot` is reachable if you need the `<img>`
directly.

## Server-side rendering

Importing this package during a server render is a no-op: the element extends a
stand-in when there is no DOM, and `register()` returns early when there is no
custom element registry. Importing it from a Next.js, Nuxt, Astro or SvelteKit
server component is safe, and the element upgrades in the browser as usual.

<Aside type="caution" title="Fixed in v3">
    In v2 this package threw `ReferenceError: HTMLElement is not defined` the moment it was imported on a server —
    before any of your own code ran. If you hit that, upgrade; see the [Migration Guide](/reference/migration/).
</Aside>

There is no declarative shadow DOM output, so the avatar itself appears on the
client. If you need the avatar in the server-rendered HTML, call `createAvatar`
directly and inline `avatar.svg` — see the SSR recipe in the
[Cookbook](/guides/cookbook/).
